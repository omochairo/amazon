# agy (Antigravity CLI) のモデル選定 — 実測記録

`scripts/bench_agy_model.py` の実測に基づく、`mine_experience.gather_antigravity` の
モデル選定記録。**結論だけ変えたくなったら、まず bench を回し直すこと。**

## 対象の切り分け — agy を使っている処理は3つ、Gemini はそのうち1つ

| 呼び出し元 | workflow | モデル | 本件の対象 |
|---|---|---|---|
| `mine_experience.gather_antigravity` | `23-experience-mining.yml` (home-ops) | **agy CLI 既定 (= Gemini)** | ✅ **これ** |
| `draft_sns_reply.call_agy` | `29-sns-reply-inbox.yml` (home-ops) | `AGY_MODEL=claude-sonnet-4-6` | ❌ Claude なので対象外 |
| `generate_faq_seo` | — | agy は使わない (owner 確定・グラウンディング制約) | ❌ 対象外 |

## なぜピンするのか

`gather_antigravity` は `agy --print` を **`--model` 無し**で叩いていた。つまり
agy CLI の既定モデルに乗る。これが困るのは:

- 既定は agy のバージョン更新で**黙って動く**（実測時点 `agy 1.1.27`）
- `agy --output-format json` の応答に**モデル名が入らない**ので、
  本番のログからは何に乗っていたか**後から特定できない**

実測でも既定は 15 回中 2 回が空応答で、成功率は全 variant 中最下位だった。
「何に乗っているか分からないものが一番不安定」という状態なので、明示ピンする。

## 実測条件

```
agy 1.1.27 / omochairo 機 (Windows) / 2026-09-06
run1  retries=0  6 variant × 5 商品 (ブランド別) × 3 trial = 90 コール
probe retries=0  6 variant × 難所 1 商品 × 5 trial        = 30 コール
run2  retries=2  6 variant × 5 商品 (ブランド別) × 3 trial = 90 コール
商品: BabyBus / ラーニングリソーシズ / プラントイ / ブリオ / ボーネルンド
```

**`--retries` は 0 と 2 の両方を測ること。** 0 は 1 コールぶんの素の完走率、
2 は本番の挙動。片方だけ見ると結論が変わる — 素だけ見ると「落ちにくいモデル」が
勝ち、リトライ後だけ見ると「当たれば良いモデル」が勝つ。

同一ブランドが per_asin に固まって並んでいるため、素直に先頭 5 件を取ると
全部 BabyBus のシールブックになる（初回はこれで回してしまい、破棄した）。
`load_products` は **1 ブランド 1 件**に絞っている。

## 採点

| 指標 | 重み | 中身 |
|---|---|---|
| `grounding` | 0.35 | 商品名・ブランドの語が本文に出るか（Web 検索が効いた証跡） |
| `balance` | 0.20 | 注意点・不満に触れているか |
| `no_refusal` | 0.20 | 「見つかりませんでした」等の逃げ文句が無いか |
| `format` | 0.15 | 箇条書き 3〜5 行（プロンプトの指示どおりか） |
| `japanese` | 0.10 | 日本語で返っているか |

失敗した trial は 0 点として平均に入れる（落ちる回数も品質のうち）。

### `balance` は後から足した — その経緯

当初は `grounding / no_refusal / format / japanese` の 4 指標だった。回してみると
**全 variant が 0.90〜0.97 に張り付いて選別できなかった**。物差しが分布の中央から
外れていて、何も選べていない状態。

本文を目視したところ、**3.1-pro 系は賞賛だけを並べて注意点を落とす**傾向が
はっきり出ていた。体験談マイニングは注意点・不満こそが記事素材の価値なので
（#3203 の凡庸化と直結する）、この差が指標に載っていないのは物差し側の欠陥。
そこで `balance` を足して再採点した。

## 結論

**`gemini-3.8-flash-low` を採用。** ただし理由は「品質が一番良いから」ではない。

### 品質では flash 系4つを区別できない

空応答にリトライを入れた後（#6580）、同条件で回し直して 2 run を合算した
（成功コール n=28〜30、score は 95% 信頼区間つき）:

```
variant                    n    mean     SE             95%CI
(default)                 28   0.915  0.017  [0.883, 0.948]
gemini-3.8-flash-medium   29   0.907  0.016  [0.875, 0.938]
gemini-3.8-flash-low      30   0.902  0.021  [0.862, 0.942]
gemini-3.8-flash-high     29   0.881  0.021  [0.839, 0.923]
gemini-3.1-pro-low        30   0.830  0.020  [0.790, 0.869]
gemini-3.1-pro-high       30   0.796  0.017  [0.763, 0.829]
```

最高（既定）との差を合成 SE で割ると:

| variant | 差 | z | 判定 |
|---|---|---|---|
| flash-low | +0.013 | 0.51 | **区別できない** |
| flash-medium | +0.009 | 0.37 | **区別できない** |
| flash-high | +0.034 | 1.27 | **区別できない** |
| 3.1-pro-low | +0.086 | 3.28 | 有意に劣る |
| 3.1-pro-high | +0.119 | 5.01 | 有意に劣る |

同じ variant を 2 回回したときの run 間ブレが最大 0.044 あり、flash 系4つの
差（0.009〜0.034）はそれに埋もれている。**品質軸ではこの4つから選べない。**

有意に言えるのは **3.1-pro が劣ること**だけ。理由は賞賛のみになりやすい点で、
これは大きな差:

| variant | 注意点ゼロ率 | 注意点の数 | 文字数 |
|---|---|---|---|
| 既定 | 0.21 | 1.36 | 454 |
| flash-low | 0.30 | 1.00 | 398 |
| flash-medium | 0.34 | 0.93 | 435 |
| flash-high | 0.41 | 1.24 | 454 |
| **3.1-pro-low** | **0.63** | 0.37 | 303 |
| **3.1-pro-high** | **0.80** | 0.20 | 298 |

推論の強いモデルが素材収集で強いとは限らない、という実測。

### 差がついたのは品質以外の軸

| variant | 素の完走率 (retry無) | 平均試行回数 (retry有) | p50 |
|---|---|---|---|
| **gemini-3.8-flash-low** | **20/20 = 1.00** | **1.00** | **12.6s** |
| flash-medium | 18/20 = 0.90 | 1.00 | 20.1s |
| flash-high | 18/20 = 0.90 | 1.00 | 31.0s |
| 既定 | 14/20 = 0.70 | **1.13** | 26.0s |

flash-low を採る理由はこの3点:

1. **既定は観測できない。** モデル名がログにも応答にも出ないので、何に乗って
   いたか後から特定できない。品質が同点でも選択肢から外れる。
2. **既定だけリトライが要る。** 空応答が多く、agy の呼び出し回数が 1.13 倍に
   なる。品質が同点ならコールは少ない方がいい。
3. **flash-low が最速** (p50 12.6s、既定の半分以下)。品質が同点なら安い方。

つまり **「品質は横並び。ならば一番安く・一番確実に返ってくるものを採る」**
が判断の実体。速さそのものが目的ではない（レイテンシは制約としてバインドして
いない — 後述）。

### 外した予想

リトライを入れれば「当たれば良いモデル」（flash-high や既定）が浮上して順位が
入れ替わるはず、と予想していたが**外れた**。リトライ後は全 variant が完走率
1.00 になり、**品質の差は最初から無かった**ことが見えただけだった。
effort を上げると出力トークンは 305→825→1282 と 4 倍になるが、
スコアには乗らない。

### レイテンシは制約としてバインドしていない

このレーンは 1 日 20 ASIN の cron で、コールあたり timeout 120s / ジョブ
timeout 60 分。20 × 26s ≈ 9 分なので、**どの variant でも時間には収まる**。
速さは決め手ではなく、品質が同点だったときのタイブレーク。

## 空応答の切り分け — 商品差ではなくモデル差だった

本ベンチの失敗 4 件は**すべて同じ ASIN (4910762116 / BabyBus シールブック)**
に集中していた。この時点では「難しい商品なので全モデルが等しく落ちる」＝
商品差の可能性があり、成功率の差をモデルの差として読むのは危険だった。

そこでこの ASIN だけに絞って 6 variant × 5 trial を追加実測した。本ベンチの
3 trial と合わせた 8 回:

```
gemini-3.8-flash-low     8/8 = 1.00
gemini-3.1-pro-low       8/8 = 1.00
gemini-3.1-pro-high      8/8 = 1.00
gemini-3.8-flash-medium  6/8 = 0.75
gemini-3.8-flash-high    6/8 = 0.75
(default)                2/8 = 0.25   ← 既定だけ壊滅
```

**商品差ではなくモデル差**。難しい商品ほど差が開き、既定モデルはこの商品で
4 回に 3 回 空応答（`status: SUCCESS` かつ `response` が空文字）を返す。

失敗モードが厄介なのは、agy が **exit 0 かつ status SUCCESS のまま空文字を返す**
こと。`gather_antigravity` は空応答を warning + skip で握るので、**レーンは緑の
まま体験談だけが入って来ない**。既定モデルに乗せたままだと、この静かな欠落が
商品によって高頻度で起きる。ピンする理由はスコアより先にこれ。

この失敗モードは **#6580 で空応答リトライ (初回 + 2 回) を入れて塞いだ**。
リトライ後は全 variant が完走率 1.00 になる。リトライ対象を空応答だけに
絞ったのは、それが実測した失敗モードだから — timeout は 1 回 120s を積み増す
だけで costly、非ゼロ終了は認証・PATH 等リトライで直らない類が主。

**ただしリトライは保険であって、モデル選定の代わりにはならない。** 既定は
リトライ後も平均 1.13 回 agy を叩いており、その差はそのまま quota に乗る。

## 下流の歩留まり — gemma は母艦から叩ける（2026-09-06 訂正）

**「gemma は K8 にしか無いので omochairo 機からは測れない」は誤りだった。**
これはハード制約ではなく**経路の穴**。K8 の Ollama は WSL2 の NAT 越しで LAN
には出ていない（`192.168.68.74:11434` は closed）が、**ssh は開いている**。
ローカルポートフォワードを 1 本張れば母艦から `/api/generate` に届く:

```bash
ssh -N -L 21434:localhost:11434 -i ~/.ssh/id_ed25519_k8 <user>@<k8-host>
curl -s http://localhost:21434/api/tags   # gemma4:26b-a4b-it-qat が見える
```

`mine_experience.py` は `--ollama-url`（既定 `OLLAMA_HOST`）を持つので
**コード変更なし**で母艦から `extract_snippets` が回る。variant 別の下流歩留まり
（agy 本文 → snippet 何本）は `scripts/bench_snippet_yield.py` で測る。本文は
このベンチの `--out` に保存済みなので、**agy を叩き直さずに**採り直せる:

```bash
python3 -m scripts.bench_snippet_yield --bench /tmp/bench.json \
    --ollama-url http://localhost:21434
```

疎通実測（2026-09-06、母艦 Windows → K8）: 1 candidate あたり gemma 45.6s、
`entailed` を通って 2 snippets（`体験談` / `不満`）。

### 本番の歩留まり — ピン前のベースライン（2026-09-06 取得）

ピン（`ANTIGRAVITY_MODEL=gemini-3.8-flash-low`, `950d866`）は 2026-09-06 に
入った。したがって **2026-09-01〜09-05 の 5 run は全部ピン前 = agy 既定モデル**で、
そのまま before として使える。ピン後 5 run が溜まったら同じ集計で after を取り、
比較すること（**この before は取り直せない**）。

| | 値 |
|---|---|
| 対象 | 100 ASIN（20 × 5 run、2026-09-01〜09-05） |
| `experience.json` を書けた率 | **91.0%**（0 本は 9 ASIN） |
| 1 ASIN あたり snippet | **3.50 本**（sd 2.27 / 中央 3 / 最大 11） |
| 本数分布 | `{0:9, 2:18, 3:41, 4:14, 5:4, 6:3, 7:1, 8:4, 9:3, 10:2, 11:1}` |

注意: これは**レーン合計**（antigravity + blog + threads + youtube + yahoo）で、
antigravity レーン単独ではない。variant 比較には使えない — それは
`bench_snippet_yield.py` 側の仕事。

**`experience.json` の件数から歩留まりは出せない。** `run_asin` は
`if not snippets: return None` で 0 本のとき**ファイルを書かない**ので、
リポジトリ側には分母が残らない（成功だけが残る = 生存者バイアス。
#5941 の「失敗と検出 0 件が区別できない」と同型）。分母は workflow ログにある:

```bash
gh run view <run-id> -R omochairo/amazon-home-ops --log \
  | grep -oE "(wrote .*/experience.json \([0-9]+ snippets\)|[A-Z0-9]{10}: 0 snippets)"
```

### variant 別の下流歩留まり — 実測（2026-09-06 夜、n=15/variant）

`bench_agy_model --trials 1 --products 5 --retries 2` を 3 バッチ回して
90 コールを取り、その本文をそのまま `bench_snippet_yield` に流した（下流も 90 件）。

```
variant                    n  up_ok  entail  snip/all     sd  snip/ok  chars   p50s
gemini-3.8-flash-low      15   1.00    0.87      2.67   1.19     2.67    340   22.7
gemini-3.1-pro-low        15   0.93    0.93      2.40   1.14     2.57    285   18.6
gemini-3.8-flash-medium   15   0.73    1.00      2.33   1.53     3.18    392   23.5
gemini-3.1-pro-high       15   0.87    0.92      2.07   1.24     2.38    282   18.0
gemini-3.8-flash-high     15   0.53    0.88      1.40   1.54     2.62    380   23.3
(default)                 15   0.27    0.75      0.67   1.45     2.50    370   21.7
```

**結論: 下流は variant を選別しない。歩留まりを決めているのは上流の完走率。**

- 変換率（`snip/ok`）は全 variant が **2.38〜3.18** に収まる（全体 2.66 / sd 1.11）。
  「返ってきさえすれば同じくらい snippet になる」
- **上流完走率とレーン本数の相関は r = 0.962**（n=6 variant）。レーン本数は
  ほぼ完走率のコピー
- `entail_rate` は 0.75〜1.00。gemma の門は狭くない
- `不満` が全 variant で最頻 aspect（flash-low は 13 本）。#3203 で欲しい
  「注意点」の素材は下流で落ちていない

**つまり variant 選定は上流の完走率だけで決めてよい。** 上流だけ見て結論を
出していた従来のやり方は、結果として正しかった。ただし——

- **上流スコア 1 位と下流 1 位は一致しない。** 上流は 3.1-pro-low（0.831）が
  1 位だが、下流 1 位は flash-low（2.67 本）。**代理指標の順位はそのまま
  本数の順位にならない**ので、スコアで選ぶのはやめて完走率で選ぶこと
- flash-medium は変換率が最高（3.18）なのに、上流 0.73 のせいでレーンでは
  2.33 本に沈む。**変換率で選ぶのも間違い**

### 同じ条件で結論が変わった — 測り直しが要る

この n=15 は、上の「結論」節と **同じ agy 1.1.27・同じ 5 商品・同じ retries=2**
で、同じ 2026-09-06 に取った。それでも数字が食い違う:

| | 先行実測 | 本実測（同日夜） |
|---|---|---|
| 完走率 | 全 variant **1.00** | **0.27〜1.00** |
| (default) | ほぼ同点（score 0.797） | **0.27 / score 0.232** で独走最下位 |
| 3.1-pro の賞賛のみ率 | 0.63 / 0.80（劣位の根拠） | **0.14 / 0.08** |
| p50 レイテンシ | 12.5〜23.0s | **39.5〜152.7s（3〜6 倍）** |

**「レイテンシはバインドしていない」は今の値では成立しない。** 先行実測の
20 ASIN × 26s ≈ 9 分に対し、本実測の p50 では 20 × 40〜150s = **13〜50 分**で、
ジョブ timeout 60 分に接近する。

`[推]` 原因は agy / Gemini 側の同日内変動（ルーティングかクォータ圧）。ベンチ側は
同一コード・同一商品集合。**一時的な劣化か新しい定常状態かは、この 1 回では
区別できない。** レーンが遅い・薄いと感じたらまずベンチを回し直すこと。

ピンの判断自体はむしろ強化された: flash-low は唯一 `1.00` を保ち、
既定は 0.27 まで落ちている。

## 測っていないもの

- **上の劣化が一時的か定常か**。日を変えて同条件で 1 回取れば分かる。
- **コスト**。agy はユーザー quota 側で、コール単価の内訳が取れない。
- **flash 系4つの品質差**。n=30 でも 95%CI が重なっており、**差が無いことを
  示したのではなく、この標本数では差を検出できていない**。区別が要るなら
  商品数を増やす（trial ではなく商品を増やす方が効く — 分散の主因は商品側）。

## 再実行

```bash
# 素の完走率
python3 -m scripts.bench_agy_model --trials 3 --products 5 --retries 0 --out /tmp/bench.json
# 本番の挙動 (gather_antigravity の _MAX_EXTRA_RETRIES に合わせる)
python3 -m scripts.bench_agy_model --trials 3 --products 5 --retries 2 --out /tmp/bench_retry.json
```

本文を記録に残しているので、採点器を直したときは**採り直さずに**採点し直せる:

```bash
python3 -m scripts.bench_agy_model --report /tmp/bench.json
```

新しいモデルが出たら `--variants` に足して回す。既定 (`--model` 無し) は
`""` で指定する。
